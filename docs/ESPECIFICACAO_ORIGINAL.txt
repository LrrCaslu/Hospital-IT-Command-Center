# PROMPT — DESENVOLVIMENTO DE PLATAFORMA NOC HOSPITALAR

## 1. Objetivo do projeto

Atue como um engenheiro de software sênior, arquiteto de sistemas, especialista em infraestrutura de redes, segurança da informação, observabilidade e desenvolvimento web.

Sua missão é desenvolver uma aplicação web profissional, denominada provisoriamente **Hospital IT Command Center**, destinada ao monitoramento, à análise e à gestão centralizada da infraestrutura de tecnologia da informação de uma rede hospitalar com múltiplas unidades.

O sistema deverá consolidar, em uma interface única, dados provenientes de:

- MikroTik — infraestrutura de rede e conectividade.
- GLPI — chamados e gerenciamento de serviços de TI.
- UniFi — infraestrutura de redes sem fio.
- Zabbix — monitoramento de servidores, equipamentos e serviços.
- Wazuh — segurança da informação e detecção de ameaças.
- Duplicati — execução e acompanhamento de backups.

O objetivo principal é permitir que a equipe de TI identifique problemas rapidamente, compreenda seu impacto, acompanhe incidentes e tome decisões sem precisar alternar constantemente entre ferramentas.

O resultado esperado é uma plataforma visualmente sofisticada, funcional, modular, responsiva, segura e preparada para ambientes corporativos.

**O sistema não deverá ser apenas uma demonstração visual. Todas as funcionalidades implementadas devem possuir comportamento real, persistência de dados, validações, regras de negócio e tratamento adequado de erros.**

# 2. Tecnologias obrigatórias

Utilizar as seguintes tecnologias:

### Backend
- PHP 8.3 ou superior.
- Laravel em versão estável compatível.
- APIs REST para comunicação interna e integrações.
- Laravel HTTP Client para consumo das APIs externas.
- Laravel Scheduler e filas para processos automatizados.
- Arquitetura baseada em Services, Jobs, Controllers, Models, Policies e DTOs quando apropriado.

### Frontend
- Blade.
- Livewire.
- Alpine.js.
- Tailwind CSS.
- Chart.js ou Apache ECharts para gráficos interativos.
- Lucide Icons.
- Vite para gerenciamento dos recursos frontend.

### Banco de dados
- MySQL 8.0 ou superior.
- Eloquent ORM.
- Migrations.
- Seeders.
- Índices e relacionamentos adequados.
- Transações nas operações que exigirem consistência.

### Ambiente local

A aplicação deverá funcionar localmente utilizando **ServBay**.

Configurações iniciais de desenvolvimento:

```env
APP_NAME="Hospital IT Command Center"
APP_ENV=local
APP_DEBUG=true
APP_TIMEZONE=America/Sao_Paulo

DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_DATABASE=hospital_it_noc
DB_USERNAME=root
DB_PASSWORD=ServBay.dev
```

O host e a porta do MySQL deverão ser confirmados de acordo com a configuração efetiva do ServBay.

Criar automaticamente as tabelas por migrations, configurar dados fictícios por seeders e entregar instruções para inicialização.

As credenciais `root` fornecidas são exclusivamente para desenvolvimento local. A aplicação deverá permitir utilizar posteriormente um usuário próprio do banco, com permissões restritas.

# 15. Atualização em tempo real

Implementar atualização automática do dashboard **a cada 10 segundos**.

### Comportamento

- Atualizar indicadores sem recarregar toda a página.
- Atualizar lista de alertas.
- Atualizar status dos equipamentos.
- Atualizar incidentes.
- Atualizar notificações.
- Atualizar gráficos de acordo com os dados recebidos.

Separar o intervalo de atualização visual do intervalo de coleta das integrações.

A interface poderá atualizar a cada 10 segundos, mas cada fonte deverá ter um intervalo de coleta próprio e configurável.

Por exemplo:

| Fonte | Intervalo inicial sugerido |
|---|---|
| MikroTik | 10–30 segundos |
| GLPI | 60 segundos |
| UniFi | 30 segundos |
| Zabbix | 30 segundos |
| Wazuh | 60 segundos |
| Duplicati | 60 segundos |

Esses intervalos são valores iniciais e deverão respeitar a capacidade, a documentação e os limites de cada API.

### Requisitos técnicos

- Executar coletas no backend.
- Nunca expor credenciais de integração no navegador.
- Utilizar filas e processos de coleta desacoplados.
- Aplicar timeouts.
- Utilizar retry com backoff.
- Evitar coletas simultâneas duplicadas.
- Controlar concorrência.
- Utilizar cache.
- Detectar dados desatualizados.
- Registrar última tentativa e última coleta bem-sucedida.
- Permitir desativar integrações individualmente.

O sistema deverá possuir processo local de coleta executável no ServBay, incluindo comando próprio para operação contínua em intervalos menores que um minuto.

Não depender exclusivamente de cron de um minuto para cumprir a atualização de 10 segundos.

Quando uma integração perder comunicação, não mostrar dados antigos como se fossem atuais.

# 23. Segurança da informação e LGPD

- Não coletar dados pessoais de pacientes.
- Não armazenar prontuários médicos.
- Não registrar senhas em logs.
- Não expor tokens em respostas.
- Não revelar topologia interna a usuários não autorizados.
- Restringir acesso a IPs e hostnames.
- Sanitizar mensagens de erro.
- Aplicar criptografia aos segredos das integrações.
- Manter trilha de auditoria.
- Implementar menor privilégio.
- Utilizar conexões seguras.
- Evitar armazenar payloads sensíveis sem necessidade.
- Controlar retenção de logs.
- Proteger downloads e relatórios com autorização.

O painel deve permitir o uso de nomes amigáveis para ativos e unidades, sem necessidade de expor os identificadores técnicos na visão executiva.

Criar telas administrativas específicas para dados sensíveis, protegidas por permissões adequadas.

A plataforma deverá iniciar com integrações em modo somente leitura.

Não implementar execução remota de comandos, alteração de firewall, reinicialização de equipamentos ou operações destrutivas como parte automática do monitoramento.

# 26. Regras de negócio essenciais

Implementar e documentar:

1. Um ativo pode pertencer a uma unidade e ser monitorado por múltiplas ferramentas.
2. A mesma ocorrência não deve gerar pontos de atenção duplicados sem necessidade.
3. Um incidente reconhecido continua ativo até sua resolução.
4. Dados antigos devem ser identificados como desatualizados.
5. Falha na coleta não significa automaticamente falha do equipamento.
6. Um serviço crítico tem maior impacto operacional que um ativo comum.
7. O encerramento de incidentes deve preservar histórico.
8. Ações dos usuários devem respeitar as permissões de acesso.
9. Dados simulados e reais nunca devem ser confundidos.
10. O backend deve continuar funcionando caso alguma integração fique indisponível.
11. Os dashboards devem apresentar estados vazios e mensagens adequadas.
12. Os processos de coleta devem ser idempotentes quando aplicável.
13. A classificação de prioridades deverá considerar impacto e urgência.
14. O sistema não deverá depender da disponibilidade simultânea das seis plataformas.
15. Todo indicador calculado deverá ter uma regra documentada.
